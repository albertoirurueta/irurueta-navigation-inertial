== The WGS84 ellipsoid and curvilinear position

Position on the Earth's surface (or above/below it) can be described either as a Cartesian ECEF vector
or, more usefully for navigation output, as *curvilinear position*: geodetic latitude stem:[L], longitude
stem:[\lambda], and height stem:[h] above the WGS84 reference ellipsoid.

image::estimators/height-and-geodetic-latitude.svg[Geodetic height and latitude of a body above the ellipsoid,620,460]

The ellipsoid is described by the equatorial radius stem:[R_0], the polar radius stem:[R_P], the flattening
stem:[f=(R_0-R_P)/R_0] and the eccentricity stem:[e=\sqrt{f(2-f)}]. Three frames take part in the
conversions of this page, and the diagram shows how they relate:

[mermaid]
....
flowchart LR
    ECEF["ECEF (x, y, z)\nCartesian, fixed to the Earth"] <-->|"L, lambda, h\n(ellipsoid geometry)"| CURV["Curvilinear\n(L, lambda, h)"]
    CURV -->|"rates: v_N, v_E, v_D\nand radii R_N, R_E"| NED["NED velocity\n(north, east, down)\nlocal tangent frame at (L, lambda, h)"]
    NED -->|"C_n^e from L and lambda"| ECEF
....

== ECEF and curvilinear conversion

With stem:[R_E(L)] the transverse radius defined in the next section, the Cartesian position of a point at
curvilinear position stem:[(L,\lambda,h)] is (Groves chapter 2, geodetic-to-Cartesian conversion):

[stem]
++++
\mathbf{r}^{e}_{eb} = \begin{pmatrix}
\left(R_{E}(L)+h\right)\cos L\cos\lambda \\
\left(R_{E}(L)+h\right)\cos L\sin\lambda \\
\left(\left(1-e^{2}\right)R_{E}(L)+h\right)\sin L
\end{pmatrix}
++++

The inverse (Cartesian to geodetic) has no closed form in terms of elementary functions for the exact
ellipsoid and is solved iteratively; longitude is simply stem:[\lambda=\operatorname{atan2}(y,x)]. The local
NED axes at that point are related to ECEF by the rotation stem:[\mathbf{C}^{e}_{n}], which depends only on
stem:[L] and stem:[\lambda]:

[stem]
++++
\mathbf{C}^{e}_{n} = \begin{pmatrix}
-\sin L\cos\lambda & -\sin\lambda & -\cos L\cos\lambda \\
-\sin L\sin\lambda & \cos\lambda & -\cos L\sin\lambda \\
\cos L & 0 & -\sin L
\end{pmatrix}, \qquad
\mathbf{v}^{e}_{eb} = \mathbf{C}^{e}_{n}\,\mathbf{v}^{n}_{eb}
++++

These conversions are not performed by the three estimators of this page; they are used around them, by the
frame and converter classes that turn an ECEF state into the NED state the estimators consume.

== RadiiOfCurvatureEstimator

Latitude and longitude do not change at a uniform linear rate per meter travelled, because the WGS84
ellipsoid is not a sphere: it is flattened at the poles. The *meridian radius of curvature*,
stem:[R_N(L)], governs north-south motion; the *transverse radius of curvature*, stem:[R_E(L)], governs
east-west motion. Both are smallest at the equator and largest at the poles:

[stem]
++++
R_{N}(L) = \frac{R_{0}\left(1-e^{2}\right)}{\left(1-e^{2}\sin^{2}L\right)^{3/2}}, \qquad
R_{E}(L) = \frac{R_{0}}{\sqrt{1-e^{2}\sin^{2}L}}
++++

where stem:[R_0] is the WGS84 equatorial radius and stem:[e] is the WGS84 eccentricity (equations 2.105 and
2.106 in the implementation). See xref:reference.adoc#book-groves[[book-groves\]], chapter 2.

Intuitively, stem:[R_N] is the radius of the circle that best fits the meridian ellipse at latitude
stem:[L], and stem:[R_E] is the distance from the surface point to the rotation axis measured along the
ellipsoid normal. On a sphere (stem:[e=0]) both collapse to stem:[R_0].

[source,java]
----
double latitude = Math.toRadians(41.3851);

RadiiOfCurvature radii = RadiiOfCurvatureEstimator.estimateRadiiOfCurvatureAndReturnNew(latitude);

double meridianRadius = radii.getRn();   // R_N(L), meters
double transverseRadius = radii.getRe(); // R_E(L), meters
----

image::estimators/geodetic-latitude.svg[Geocentric vs. geodetic latitude on the WGS84 ellipsoid,560,380]

Both `NEDPositionEstimator` and `NEDVelocityEstimator` use these radii to convert between the NED
velocity stem:[(v_N, v_E, v_D)] and the rate of change of curvilinear position. A north displacement
stem:[v_N\,dt] subtends an angle stem:[v_N\,dt/(R_N+h)] at the centre of curvature; an east displacement
travels on a parallel of radius stem:[(R_E+h)\cos L], and down velocity is minus the height rate:

[stem]
++++
\dot L = \frac{v_{N}}{R_{N}(L)+h}, \qquad
\dot\lambda = \frac{v_{E}}{\left(R_{E}(L)+h\right)\cos L}, \qquad
\dot h = -v_{D}
++++

== NEDPositionEstimator

Integrates curvilinear position forward over one time step from the old and new NED velocity, using the
trapezoidal (average of old/new rate) integration of the position-rate equations above (equation 5.56 in the
code comments). In Groves §5.4 this is the position-update step of the NED navigation equations:

[stem]
++++
h(+) = h(-) - \frac{1}{2}\tau_i\left(v_D(-) + v_D(+)\right)
++++

[stem]
++++
L(+) = L(-) + \frac{1}{2}\tau_i\left(\frac{v_N(-)}{R_N(L(-))+h(-)} + \frac{v_N(+)}{R_N(L(-))+h(+)}\right)
++++

[stem]
++++
\lambda(+) = \lambda(-) + \frac{1}{2}\tau_i\left(\frac{v_E(-)}{(R_E(L(-))+h(-))\cos L(-)} + \frac{v_E(+)}{(R_E(L(+))+h(+))\cos L(+)}\right)
++++

Height, then latitude, then longitude must be updated in that order, since each subsequent equation
depends on the previous result. The latitude update uses the meridian radius at the old latitude together with the new height,
while the new-velocity term of the longitude update uses the transverse radius re-evaluated at the newly
updated latitude.

[source,java]
----
double timeInterval = 1.0; // seconds
double oldLatitude = Math.toRadians(41.3851);
double oldLongitude = Math.toRadians(2.1734);
double oldHeight = 0.0;
double oldVn = 1.0, oldVe = 0.0, oldVd = 0.0; // previous NED velocity (m/s)
double vn = 1.0, ve = 0.0, vd = 0.0;          // current NED velocity (m/s)

NEDPosition newPosition = NEDPositionEstimator.estimatePositionAndReturnNew(
        timeInterval, oldLatitude, oldLongitude, oldHeight, oldVn, oldVe, oldVd, vn, ve, vd);

double newLatitude = newPosition.getLatitude();
double newHeight = newPosition.getHeight();
----

== NEDVelocityEstimator

The inverse operation: given curvilinear position at two epochs, estimate the average NED velocity
between them by finite-differencing latitude/longitude/height and then inverting the same trapezoidal
relation used above (equation 5.56 solved for the new velocity: the average rate is stem:[\dot L], so
stem:[v_N(+)/(R_N+h(+)) = 2\dot L - v_N(-)/(R_N(L(-))+h(-))]):

[stem]
++++
v_N(+) = \left(R_N(L(-))+h(+)\right)\left(2\dot L - \frac{v_N(-)}{R_N(L(-))+h(-)}\right)
++++

[stem]
++++
v_E(+) = \left(R_E(L(+))+h(+)\right)\cos L(+)\left(2\dot\lambda - \frac{v_E(-)}{\left(R_E(L(-))+h(-)\right)\cos L(-)}\right)
++++

[stem]
++++
v_D(+) = -2\dot h - v_D(-)
++++

This is mainly useful for turning a sequence of positions (e.g., from a reference trajectory or a GNSS
log) into the velocity time series needed as input to xref:estimators/kinematics.adoc[kinematics
estimators] or a xref:navigators/index.adoc[navigator] initialization step.

[source,java]
----
double timeInterval = 1.0; // seconds
double oldLatitude = Math.toRadians(41.3851);
double oldLongitude = Math.toRadians(2.1734);
double oldHeight = 0.0;
double oldVn = 1.0, oldVe = 0.0, oldVd = 0.0; // previous NED velocity (m/s)

// current position, e.g. the next GNSS fix in a log
double latitude = Math.toRadians(41.38511);
double longitude = oldLongitude;
double height = 0.0;

NEDVelocity velocity = NEDVelocityEstimator.estimateVelocityAndReturnNew(
        timeInterval, oldLatitude, oldLongitude, oldHeight, oldVn, oldVe, oldVd,
        latitude, longitude, height);

double vn = velocity.getVn();
----
